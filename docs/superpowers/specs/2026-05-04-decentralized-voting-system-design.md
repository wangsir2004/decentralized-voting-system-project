# 去中心化电子投票系统设计规格

## 1. 项目目标

本项目实现一个基于 Solidity 智能合约与 Ethereum 测试网的去中心化电子投票系统。系统以工程完整型 MVP 为主线，优先保证「可运行、可测试、可部署、可演示、可写入论文」。

系统需要覆盖以下目标：

- 通过智能合约完成投票流程，降低中心化投票系统中的单点故障和人为篡改风险。
- 在 Sepolia 测试网上完成部署和演示，记录合约地址、ABI、交易 Hash 和 Gas 数据。
- 使用 React DApp 完成钱包连接、提案展示、投票提交、交易反馈和结果可视化。
- 在论文中完成区块链、ECDSA、哈希、Merkle Tree、Gas 消耗和合约安全的理论分析。

## 2. 制作路线

采用「工程完整型 MVP + 论文增强」路线：

- 第一目标：完成完整可运行系统，确保答辩现场能演示完整链路。
- 第二目标：用 Merkle Tree 白名单、ECDSA 签名说明、Gas 统计和安全审计增强论文深度。
- 不引入零知识证明、环签名等复杂匿名协议，匿名性定位为 Ethereum 地址层面的伪匿名。

该路线的好处是实现难度可控，同时能满足任务书对系统实现、测试网部署、数学论证和安全验证的要求。

## 3. 技术栈

### 3.1 智能合约与开发环境

- Solidity：编写投票智能合约。
- Hardhat：本地编译、测试、部署脚本和测试网部署。
- OpenZeppelin：复用 `Ownable`、`MerkleProof` 等成熟组件。
- Sepolia：首选 Ethereum 测试网。
- Slither 或 Remix 静态分析器：进行合约安全检查。

### 3.2 前端 DApp

- React + Vite：构建前端应用。
- TypeScript：提升前端类型可靠性。
- Ethers.js：连接钱包、读取合约、发送交易。
- ECharts：展示投票结果图表。
- MetaMask：用户钱包连接与交易签名。

### 3.3 文档与论文材料

- Markdown：记录开发过程、部署步骤、测试记录和 Gas 数据。
- Mermaid：绘制系统架构图、数据流图和用例图。
- 表格：整理测试用例、Gas 消耗和安全分析。

## 4. 系统角色

系统包含 3 类角色：

- 管理员：部署合约、创建投票、设置候选项、设置投票截止时间、配置选民白名单 Merkle Root。
- 选民：连接钱包、查看投票信息、提交一次投票、查看交易状态。
- 访客/审查者：无需投票权限即可查看投票状态、候选项和统计结果。

## 5. 功能范围

### 5.1 MVP 必做功能

- 钱包连接：识别 MetaMask、连接账户、显示当前账户和网络。
- 网络校验：提示用户切换到 Sepolia 或本地 Hardhat 网络。
- 投票展示：展示投票标题、候选项、截止时间、投票状态。
- 白名单校验：使用 Merkle Proof 验证选民是否具备投票资格。
- 防重复投票：同一地址只能成功投票一次。
- 投票提交：选民选择候选项并发起链上交易。
- 结果统计：合约记录票数，前端展示实时结果。
- 事件记录：合约发出创建投票、投票成功等事件，便于论文说明可追溯性。
- 测试网部署：部署到 Sepolia 并保存合约地址、ABI 和部署交易 Hash。

### 5.2 论文增强功能

- Merkle Tree 白名单：论文中说明 `O(log n)` 验证优势。
- ECDSA 签名说明：结合 MetaMask 交易签名解释地址伪匿名和身份控制。
- Gas 评估：统计部署、投票、读取结果等操作的 Gas 消耗。
- 安全分析：覆盖重复投票、越权操作、投票截止时间、无效候选项、重入攻击适用性。

### 5.3 暂不纳入范围

- 不实现真正匿名投票或零知识证明。
- 不实现链下身份实名审核系统。
- 不实现多轮复杂治理系统。
- 不实现移动端 App，仅保证 Web 响应式访问。

## 6. 智能合约设计

### 6.1 合约名称

主合约命名为 `VotingSystem`。

### 6.2 核心状态

合约应维护以下核心状态：

- `owner`：管理员地址，由 OpenZeppelin `Ownable` 管理。
- `title`：投票主题。
- `candidates`：候选项列表。
- `voteCounts`：候选项得票数。
- `votingEndTime`：投票截止时间。
- `merkleRoot`：选民白名单根节点。
- `hasVoted`：记录地址是否已投票。

### 6.3 核心接口

合约需要提供以下接口：

- `constructor(title, candidates, votingEndTime, merkleRoot)`：初始化投票。
- `vote(candidateIndex, merkleProof)`：提交投票。
- `getCandidates()`：返回候选项列表。
- `getResults()`：返回候选项及票数。
- `isVotingOpen()`：返回投票是否仍在开放状态。
- `hasAddressVoted(address)`：查询地址是否已投票。

### 6.4 安全约束

- 投票截止时间必须晚于部署时间。
- 候选项数量必须大于等于 2。
- 候选项索引必须有效。
- 投票地址必须通过 Merkle Proof 白名单校验。
- 同一地址不能重复投票。
- 截止时间后不能投票。
- 合约不向外部地址转账，重入攻击风险较低，但论文仍需说明原因。

## 7. 前端设计

### 7.1 页面结构

前端采用单页 DApp，包含以下区域：

- 顶部栏：系统名称、网络状态、钱包连接按钮。
- 投票信息区：标题、截止时间、投票状态、当前账户资格状态。
- 候选项区：候选项列表、单选操作、提交投票按钮。
- 交易反馈区：等待签名、交易发送、链上确认、失败原因。
- 结果可视化区：票数列表和 ECharts 图表。
- 论文演示区：展示合约地址、网络、交易 Hash 和 Gas 统计入口。

### 7.2 前端状态

前端需要维护以下状态：

- 当前账户地址。
- 当前网络 Chain ID。
- 合约连接状态。
- 候选项和票数。
- 用户是否已投票。
- 用户是否在白名单中。
- 当前交易状态。
- 错误提示。

### 7.3 错误处理

前端需清晰处理以下异常：

- 未安装 MetaMask。
- 用户拒绝连接钱包。
- 用户拒绝签名或交易。
- 网络不正确。
- 不在白名单。
- 已经投过票。
- 投票已截止。
- 合约读取或交易失败。

## 8. 数据流

### 8.1 投票流程

1. 用户打开 DApp。
2. 前端检查 MetaMask 是否存在。
3. 用户连接钱包。
4. 前端校验网络是否为 Sepolia 或本地网络。
5. 前端读取链上投票信息和结果。
6. 前端根据当前地址生成或读取 Merkle Proof。
7. 用户选择候选项并提交投票。
8. MetaMask 弹出交易签名。
9. 交易上链后合约更新票数并发出事件。
10. 前端刷新结果图表。

### 8.2 部署流程

1. 准备候选项列表和选民地址列表。
2. 使用脚本生成 Merkle Tree 和 `merkleRoot`。
3. 使用 Hardhat 编译合约。
4. 运行单元测试。
5. 配置 Sepolia RPC 和部署私钥。
6. 执行部署脚本。
7. 保存合约地址、ABI、部署交易 Hash 和 Gas 数据。
8. 前端读取部署产物并连接测试网合约。

## 9. 测试策略

### 9.1 合约单元测试

必须覆盖以下测试：

- 初始化成功。
- 候选项少于 2 个时部署失败。
- 截止时间早于当前时间时部署失败。
- 白名单地址可以投票。
- 非白名单地址不能投票。
- 同一地址不能重复投票。
- 投票截止后不能投票。
- 无效候选项索引不能投票。
- 投票后票数正确增加。
- `getResults()` 返回结果正确。

### 9.2 前端集成测试

前端至少手动验证以下流程：

- 未连接钱包时的界面状态。
- 连接钱包后的账户显示。
- 错误网络提示。
- 提交投票后的交易状态变化。
- 投票成功后结果图表刷新。
- 已投票账户再次投票时的提示。

### 9.3 安全与性能验证

- 使用 Hardhat 测试覆盖常见越权与边界场景。
- 使用 Slither 或 Remix 静态分析器记录合约审计结果。
- 统计部署、成功投票、失败投票场景的 Gas 消耗。
- 对重入攻击做说明性验证：合约不调用外部转账，不暴露可重入资金路径。

## 10. 论文交付映射

系统实现与论文内容对应如下：

- 绪论：传统中心化投票痛点与区块链方案动机。
- 相关技术：Ethereum、Solidity、智能合约、ECDSA、Merkle Tree、DApp。
- 需求分析：管理员、选民、访客角色和功能需求。
- 系统设计：架构图、数据流图、用例图、合约状态设计。
- 系统实现：Solidity 合约、Hardhat 部署、React 前端、Ethers.js 调用。
- 测试分析：功能测试、边界测试、安全分析、Gas 消耗表。
- 总结展望：系统不足，例如伪匿名而非完全匿名，未来可引入零知识证明。

## 11. 验收标准

系统达到以下条件视为 MVP 完成：

- 本地 Hardhat 测试全部通过。
- 合约可以部署到 Sepolia，并有明确部署记录。
- 前端可以连接 MetaMask 并读取测试网合约。
- 白名单账户可以成功投票，非白名单账户不能投票。
- 同一账户不能重复投票。
- 截止时间后不能继续投票。
- 前端能展示投票结果图表。
- 项目包含部署说明、测试说明、Gas 记录和论文材料草稿。

## 12. 风险与应对

- 测试网 RPC 不稳定：保留本地 Hardhat 网络演示方案，测试网作为最终部署记录。
- Sepolia 测试 ETH 不足：提前准备 Faucet 获取测试币。
- MetaMask 网络问题：前端提供明确网络切换提示。
- Merkle Proof 前端生成复杂：先用脚本生成白名单和 proof JSON，再由前端读取。
- 论文理论深度不足：在实现阶段同步记录 ECDSA、哈希、Merkle Tree、Gas 和安全分析材料。
- 时间不足：优先保证合约、测试、前端投票流程和部署记录，视觉细节后置。
