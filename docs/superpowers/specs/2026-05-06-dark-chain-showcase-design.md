# 暗链投票安全控制台展示优化设计规格

## 1. 目标

将当前去中心化投票 DApp 从基础操作面板升级为「暗链投票安全控制台」风格的项目展示页面。页面需要同时满足 3 个场景：

- **答辩演示：** 首屏呈现区块链系统的技术密度，让观众快速理解这是链上投票系统。
- **真实操作：** 保留 MetaMask 连接、白名单资格判断、候选项选择、提交投票和结果刷新能力。
- **论文取证：** 展示合约地址、部署交易、Merkle Root、Gas、安全约束、ABI 摘要和测试入口等可写入论文的证据。

用户已确认采用「A. 暗链指挥舱」方向，并要求在此基础上继续强化高深区块链感。

## 2. 视觉方向

页面采用深色链上控制台风格：

- **主色：** 近黑背景、荧光青绿色、少量金色高亮。
- **质感：** 网格背景、扫描线、半透明深色面板、细边框、合约终端文本、哈希数据块。
- **关键视觉：** 首屏中心放置链路拓扑，把 MetaMask、Merkle Proof、VotingSystem 合约、VoteCast 事件和结果图表串成一条证据链。
- **边界：** 不做纯装饰性炫技。所有酷感元素都服务于解释系统结构和链上证据。

该方向比普通仪表盘更具区块链项目辨识度，但仍保持答辩现场可读性。

## 3. 页面结构

### 3.1 顶部 HUD

顶部显示系统名称、当前网络、技术栈标签和关键链上标识：

- 系统名：`VotingSystem Dark Chain Command`
- 技术标签：Solidity、Hardhat、Ethers.js、Merkle Proof
- 动态数据：Chain ID、合约地址缩写、当前账户缩写

顶部 HUD 只展示高频状态，不承载复杂操作。

### 3.2 首屏控制台

首屏分为 3 个区域：

- **左侧项目概览：** 标题、系统定位、关键指标（Chain ID、部署 Gas、白名单数量、Merkle 复杂度）。
- **中间链路拓扑：** 用节点图展示钱包、白名单、合约、事件、图表之间的关系。
- **右侧合约终端：** 以终端风格展示部署交易、Merkle Root、`vote(candidateIndex, merkleProof)`、安全约束和错误拒绝场景。

首屏必须在桌面端一屏内看到主要视觉；移动端改为单列堆叠。

### 3.3 投票操作区

保留当前核心交互，并升级信息层次：

- 钱包连接状态和网络校验独立成状态面板。
- 投票主题、截止时间、开放状态、白名单资格、是否已投票组成「资格矩阵」。
- 候选项以可点击选项块呈现，显示序号和当前票数。
- 提交按钮根据账户、网络、资格、投票状态和交易状态自动禁用。
- 交易 Hash 成功产生后，作为链上证据显示在操作区下方。

### 3.4 结果与审计区

结果图表不再孤立展示，而是和审计数据放在一起：

- ECharts 柱状图展示实时票数。
- 旁边显示总票数、领先项、候选项数量和合约读取状态。
- 链上证据卡展示合约地址、部署者、部署交易、部署 Gas、部署时间和 ABI 方法摘要。

### 3.5 算法与安全区

新增论文展示细节：

- Merkle Root 和当前账户 Proof 深度。
- `MerkleProof.verify`、防重复投票、截止时间、候选项索引校验等安全约束。
- Hardhat 测试和 Gas 报告命令入口说明。

该区域只展示现有系统事实，不引入未实现的零知识证明或匿名投票承诺。

## 4. 组件设计

### 4.1 `App.tsx`

负责组装页面，读取部署配置和投票状态。新增派生展示数据：

- `totalVotes`
- `leadingCandidate`
- `shortAddress`
- `networkLabel`
- `proofDepth`

保持业务逻辑集中在 hooks 中，不把合约调用散落到展示组件。

### 4.2 `WalletPanel.tsx`

升级为「钱包与网络状态」面板：

- 显示账户缩写、当前 Chain ID、目标 Chain ID。
- 网络错误使用明确的红色状态。
- 按钮文案保持可理解，不使用过度技术化文案。

### 4.3 `VotingPanel.tsx`

升级为「链上投票执行」面板：

- 展示资格矩阵。
- 候选项显示为高密度可选块。
- 提交按钮和交易 Hash 保留。
- 禁用原因通过状态标签自然表达。

### 4.4 `ResultsChart.tsx`

升级图表视觉：

- 暗色主题。
- 青绿到金色柱状渐变。
- Tooltip 和轴线适配深色背景。
- 空数据时显示稳定占位，不让图表塌陷。

### 4.5 新增展示组件

新增组件用于降低 `App.tsx` 复杂度：

- `CommandHero.tsx`：首屏控制台和链路拓扑。
- `EvidencePanel.tsx`：合约部署、ABI 和链上证据。
- `SecurityPanel.tsx`：Merkle 与安全约束说明。
- `ShowcaseMetric.tsx`：复用关键指标卡。

## 5. 数据来源

页面只使用当前项目已有数据：

- `apps/web/public/deployment.json`：网络、合约地址、部署者、标题、候选项、截止时间、Merkle Root、部署交易、Gas、ABI。
- `apps/web/public/whitelist.json`：白名单地址、Leaf、Proof。
- `useWallet()`：账户、Chain ID、连接状态、钱包错误。
- `useVotingContract()`：候选项、票数、开放状态、资格、是否已投票、交易 Hash、加载状态、提交状态。

若部署文件缺少某项数据，页面显示「未记录」，不伪造值。

## 6. 响应式设计

- 桌面端：首屏采用三栏布局，操作区与结果审计区采用两栏或网格。
- 平板端：首屏拓扑图保持完整，左右信息区上下堆叠。
- 手机端：所有面板单列，拓扑图缩小但不裁切；长地址允许换行。

所有按钮、标签和地址文本必须在 320 px 宽度下不溢出。

## 7. 错误处理

页面需清晰处理以下状态：

- 未安装 MetaMask。
- 用户未连接钱包。
- 当前网络与部署网络不一致。
- 当前账户不在白名单中。
- 当前账户已投票。
- 投票已截止。
- 部署配置或白名单读取失败。
- 合约读取或交易提交失败。

错误文案使用中文自然表达，保留原始错误信息时需避免撑破布局。

## 8. 测试策略

前端当前没有专门测试框架，因此本次实现以可构建验证和手工验证为主：

- 运行 `npm run web:build` 验证 TypeScript 和 Vite 构建。
- 运行 `npm test` 验证智能合约测试仍通过。
- 启动 `npm run web:dev` 后，在浏览器检查桌面与移动宽度下的页面布局。
- 手动验证未连接钱包、错误网络、白名单账户、非白名单账户和交易 Hash 展示状态。

若实现过程中新增纯函数或可独立测试的格式化函数，应优先为其添加测试；否则不为了 UI 样式强行引入测试框架。

## 9. 验收标准

本次优化完成后应满足：

- 首屏明显呈现暗色区块链控制台风格，而不是普通卡片页面。
- 页面展示合约、Merkle、Gas、部署交易、ABI、安全约束等项目细节。
- 原有钱包连接、投票、结果图表流程不被破坏。
- 中文文案无乱码，中英文和数字排版规范。
- 桌面和移动端无明显文本重叠、溢出或图表空白。
- `npm run web:build` 和 `npm test` 可通过。
